# 루틴/자동화 (Rules) and 휴가/장기 외출 모드

Brand-neutral automation over the canonical capability model. Rules talk about `curtain`, `power`
(lights), `lock`... and device *kinds*/rooms, never about Samsung or LG, so they work for every adapter.

## New capabilities

* **`curtain`** (kind `curtain`): actions `open`, `close`, `stop`, `setPosition{position 0..100}`;
  state `position` (100 = fully open) and `status` (`open|closed|opening|closing|partial|unknown`);
  UI hint `curtain-controls`. Mapped in `hub/homehub/mappings.py` to SmartThings `windowShade` (+
  `windowShadeLevel`) and Matter WindowCovering (0x0102).
* **Lights** need no new capability: `kind == "light"` + `power` (+ `brightness`, `color`). SmartThings
  `switch` and the legacy `light` capability both map to `power`.
* SmartThings adapter (Python `adapters/smartthings.py`, Dart `smartthings_client.dart`, kept identical):
  `windowShade` open/close/pause (pause -> `stop`, only offered if the shade lists it in
  `supportedWindowShadeCommands`); a shade with only `windowShadeLevel` emulates open/close with
  `setShadeLevel` 100/0; category Blind/Curtain sets the kind.
* Demo hub (`HOMEHUB_FAKE_DEVICES=1`): `demo:light-living`, `-kitchen`, `-bath`, `demo:curtain-bedroom`,
  `demo:curtain-living`, `demo:cam-entrance` (drop the camera after merging `feature/cctv`).

## Rule model (same JSON in Python and Dart)

```json
{"id": "r1", "name": "취침 시 커튼 닫기", "enabled": true, "template": "bedtime-close-curtains",
 "trigger":    {"type": "allLightsOff"},
 "conditions": [{"type": "timeWindow", "start": "22:00", "end": "02:00"}],
 "actions":    [{"selector": {"capability": "curtain"}, "capability": "curtain", "action": "close"}]}
```

* Triggers: `time{at,days}`, `allLightsOff`, `deviceState{selector,capability,field,equals,match}`,
  `event{name}`.
* Conditions: `timeWindow` (crosses midnight, end exclusive), `days`, `allLightsOff`, `anyLightOn`,
  `deviceState`.
* Actions: canonical command sent to every device the selector `{deviceId,kind,room,capability}` matches
  that supports it. Commands that change nothing are skipped (`already-closed`, ...) and logged as such.
* Time triggers fire up to 10 min late (tick jitter, app opened late) and at most once per day; a rule
  created/enabled after its time today does not fire retroactively. Offline lights are ignored by
  "all lights off". Without a previous snapshot (first look) state-change triggers cannot fire.

The evaluation is a **pure function** (`hub/homehub/automation/engine.py`, line-for-line Dart port
`app/lib/automation/engine.dart`). Both run `app/test/fixtures/automation_scenarios.json` (32 scenarios,
generated by `app/tool/gen_automation_scenarios.py`), so the two engines cannot drift apart.

## Where rules run

| Mode | Engine | Runs when |
|---|---|---|
| **Hub** | `hub/homehub/automation/` (`AutomationService.run_forever`, started by the FastAPI lifespan; tick 20 s, cloud refresh 60 s) | always, app closed or not |
| **Direct cloud** | `app/lib/automation/automation_controller.dart` | **only while the app is open in the foreground** (device updates + 30 s tick, catch-up on resume). Best effort. |
| **Samsung's cloud** (optional, direct mode) | SmartThings Rules API | always, no server of ours – see below |
| **Premium server** (future) | same engine as the hub, server side | always |

**Reliable unattended automation in serverless mode is not possible from the app alone**: iOS/Android
suspend background apps, so a 07:00 "open curtains" or "all lights off after 22:00" cannot be guaranteed.
It needs a hub, the premium server, or SmartThings' own rules.

Hub HTTP API (writes need the token if `HOMEHUB_TOKEN` is set):
`GET/POST /automation/rules`, `PUT/DELETE /automation/rules/{id}`, `POST /automation/rules/{id}/enable`,
`GET/DELETE /automation/log`, `POST /automation/events/{name}`, `GET/PUT/DELETE /automation/away`;
WebSocket `{"type":"automation","entry":...}` when a rule fires. Env: `HOMEHUB_TZ` (e.g. `Asia/Seoul`;
default = the hub's local zone), `HOMEHUB_AUTOMATION=0` (off), `HOMEHUB_AUTOMATION_TICK`,
`HOMEHUB_AUTOMATION_REFRESH`. State is in `HOMEHUB_DATA/automation.json`.

## Templates in the app (규칙 추가)

`취침 시 커튼 닫기` (all lights off inside a bedtime window), `기상 시 커튼 열기` (time),
`기상 신호로 커튼 열기` (event `wake`, e.g. an alarm shortcut), `외출 시 조명 끄기`, `외출 시 도어락 잠그기`,
`외출 시 커튼 닫기`, `귀가 시 거실 조명 켜기`, and `휴가/장기 외출 모드` (below). Templates are dimmed when the
home lacks the needed devices. The screen also has the enable/disable switch, delete, and a run log
(what ran, why, which device, skipped/failed).

### Leaving / arriving

There is **no reliable geofence** available to us: SmartThings has no presence source we can read through
its public API, and background location in a serverless app is subject to the same suspension problem.
So leaving/arriving are **signals**: rules with trigger `event{leaving|arriving|wake|...}`, fired by a
button in the app, an iOS Shortcuts / Android Tasker automation calling
`POST /automation/events/leaving` on the hub, or the premium server later. Real presence detection
(phone geofence via the relay, Wi-Fi presence on the hub) is remaining work.

## SmartThings Rules / Scenes API – can automation run in Samsung's cloud?

Researched, implemented where practical:

* **Rules API** (`POST https://api.smartthings.com/v1/rules?locationId=...`) – a PAT with
  `r:rules:* w:rules:* x:rules:*` (plus device/location read) can create rules that run in Samsung's cloud
  (or locally on a Samsung hub). **Implemented as an opt-in export**: rule menu -> "Samsung 클라우드에
  등록" (direct mode + SmartThings token only). `app/lib/automation/st_rules_exporter.dart` converts a
  rule: time triggers -> `every.specific` (reference Midnight + minute offset, `daysOfWeek`, location time
  zone), bedtime windows -> `if.between` on time, all-lights-off -> `changes(equals off, aggregation All)`,
  curtain/light commands -> `command` actions grouped per component. After registering, the app stops
  evaluating that rule locally (no double firing); "해제" deletes it in Samsung's cloud.
  Refused with a Korean reason: event/signal triggers, anything touching non-SmartThings devices,
  `toggle`, non-lights in "all lights off". **The JSON shapes follow the public docs but were never sent
  to Samsung** – unverified; some community reports mention 403s for certain token types.
* **Scenes API** – normal tokens can list and execute scenes; creating them is restricted. Not used.
* Consequence: for SmartThings-only homes in direct mode, "취침 시 커튼 닫기" and "기상 시 커튼 열기" can
  run unattended without our server (if the export works on a real account). Anything cross-brand, or
  event-based, still needs the hub/premium server.

## 휴가/장기 외출 모드 (away mode / presence simulation)

Makes the home look lived in while the family is away. **Only lights and curtains are ever controlled –
never heating, cooling, appliances, locks** (enforced in code, see Safety).

Plan (one per home): start/end date, evening window (default 18:30–23:00, may cross midnight, 1–16 h), lights
by room and/or device, optional curtains (open in the morning, close at the window start), mode:

* **fixed** (`정해진 시간`) – chosen lights stay on for the whole window every evening;
* **random** (`무작위`) – every light gets its own believable pattern per day inside the window:
  living room a long evening (starts near the beginning, on for ~half to three quarters of the window),
  kitchen one or two short visits early (15–35 min, second 10–20 min), bathroom 1–3 brief visits (5–15 min),
  bedroom late then off, entrance a while at dusk, other rooms one 30–90 min stretch. Curtains get ±15 min
  of jitter. Times come from a **seeded** integer generator (Park-Miller) keyed by seed + day + device id:
  reproducible for tests, different from day to day, identical in Python and Dart.

After the last evening's window everything is off and the plan is finished. `arriving` (signal) ends the
plan early and turns off only the lights the plan itself turned on (a light that was already on stays).

Design: `wants(plan, now, devices)` (pure) says what the home should look like *right now*; the service
sends only the difference. A missed tick, an app restart or a hub reboot therefore never leaves the
schedule wrong. Failed commands are retried at most every 5 min.

* Hub: `hub/homehub/automation/away.py` + `AutomationService` (always on; API `GET/PUT/DELETE
  /automation/away`, run log entries named "휴가 모드 · 휴가 모드 3일째").
* App, direct mode: `app/lib/automation/away.dart` (Dart port; shared fixture
  `app/test/fixtures/away_scenarios.json`, generated from Python by `app/tool/gen_away_scenarios.py`) –
  foreground/best effort only; the setup screen says so. In hub mode the app only edits the plan.
* UI: rules -> 규칙 추가 -> `휴가/장기 외출 모드`; the summary card shows "휴가 모드 켜짐, 3일째"; the plan
  screen shows today's generated schedule per light and "귀가 · 종료".
* **Samsung delegation: not done.** A random schedule is regenerated daily; the Rules API has no
  randomness, so only the *fixed* mode could be exported (one `every` rule per light and time). Not
  implemented; the fixed mode is the candidate if wanted.

### Safety

`away.py` only selects `kind == "light"` devices with `power.turnOn` and devices with the `curtain`
capability, and only produces `turnOn/turnOff/open/close`. The service (`_away_step`) and the Dart
controller re-check every command against that allow-list before sending, even if a plan lists a heater or
lock by id (tested with an air conditioner and a lock).

## Tier mapping suggestion (documentation only – not enforced anywhere)

Current table in `premium-server.md`: push = Pro+, 자동화 규칙 = Mmax only. Suggested change:

| Feature | Free | Pro | Max | Mmax |
|---|---|---|---|---|
| Home Summary (screen, card, local notifications) | yes | yes | yes | yes |
| Push while app closed (relay) | - | yes | yes | yes |
| Rules, app-side (foreground) and self-hosted hub | yes (costs us nothing) | yes | yes | yes |
| Server-side rules (relay runs them 24/7) | - | - | limited (e.g. 10 rules) | more (100 rules, per the draft) |
| 휴가/장기 외출 모드 (server-side) | - | - | yes | yes |
| Samsung-cloud export | yes (runs on Samsung, no server) | yes | yes | yes |

Rationale: we should only charge for what costs us to run (the 24/7 server engine and push); rules on the
user's own hub or in Samsung's cloud are free. The away mode is the strongest reason to want an always-on
server (people travel), so it is a natural Max feature.

## Unverified / remaining

  the Android/iOS notification setup are unverified on hardware; the Android build with desugaring was not
  run (no Android SDK on the dev box).

* Real presence (geofence/Wi-Fi), server-side rules and push (premium relay), SmartThings export for the

* `feature/cctv` is merged in `feature/integrated`: `demo:cam-entrance` was dropped; the demo cameras
  (`demo:cam-living`, `demo:cam-door`) carry the `sensor` readings (`visitorCount`, `motion`) the Home Summary reads.
