## 0. 한눈에 보기 (요약)

- 앱은 **기본적으로 서버 없이(serverless)** 동작합니다. 폰이 SmartThings / LG ThinQ 클라우드를 직접 호출합니다. 이 기본 동작은 **그대로 무료**로 유지합니다.
- **프리미엄 서버**는 "있으면 편한 것"을 돈 받고 제공하는 **선택 사항**입니다. 서버가 없어도 앱은 100% 동작해야 합니다.
- 앱 안에는 이미 "백엔드 연결 방식"을 바꿔 끼울 수 있는 구조(직접 클라우드 `DirectCloud` / 집 허브 `Hub` / 앞으로 `Premium`)가 있으므로, 프리미엄 서버는 **세 번째 끼우개**로 추가합니다. 앱 화면은 바뀌지 않습니다.
- 서버는 **FastAPI(파이썬) + PostgreSQL** 로 작게 시작하고, 지금 `hub/` 에 있는 기기 어댑터(SmartThings, Roborock 등)를 **최대한 재사용**합니다.
- ⚠️ **가장 큰 사업적 위험 3가지**
  1. **1,000원 요금제는 스토어 수수료·세금·서버 비용을 빼면 남는 것이 거의 없음** (7장).
  2. **SmartThings가 2026년 10월부터 API를 유료화**한다고 발표함 (개인 개발자용 월 $4.99 플랜, 상업용 별도 요금제). 프리미엄 서버가 사용자 대신 SmartThings를 호출하면 **상업용 계약 대상**일 가능성이 큼 (3~4절 참고, 확인 필요).
  3. Roborock 연동은 현재 **비공식(리버스 엔지니어링)** 방식이라, 유료 서비스로 팔기에는 약관 위험이 큼.

설계 원칙:
- **한도는 서버 설정값(DB)** 으로 두어 앱 업데이트 없이 바꿀 수 있게 합니다. (관리자 화면의 "기능 플래그/한도" 메뉴, 6장)
- "무제한"은 진짜 무제한이 아니라 **공정 사용 정책**(남용 방지용 상한)을 둡니다.
- 한도 초과 시에는 요금을 더 받지 않고 **일시적으로 느려지거나 거절**하고, 앱에 "한도에 도달했어요" 안내를 띄웁니다.
- Free는 **서버를 아예 쓰지 않으므로** 기기 5대 제한은 서버가 아니라 **앱이 스스로** 지킵니다. (우회가 쉬운 소프트 제한임을 인정. 우회를 막는 것이 목적이 아니라 유료 전환의 동기입니다.)

## 2. 전체 구조(아키텍처)

### 2-1. 큰 그림

```
                      ┌────────────────────────── 프리미엄 서버 ──────────────────────────┐
  [폰 앱] ── HTTPS ──▶│ API (FastAPI)  ─┬─ 계정/인증      ─┐                              │
  iOS/Android         │                 ├─ 구독/결제 검증  ├─ PostgreSQL (사용자·구독·기기·로그)
     ▲                │                 ├─ 기기 제어(어댑터 재사용)                        │
     │ 푸시            │ 작업자(Worker) ─┴─ 상태 확인·알림·자동화 ── Redis(대기열/속도제한)  │
     │ (APNs/FCM)     └────┬──────────────┬─────────────────────┬─────────────────────────┘
     │                     │              │                     │
     └─────────────────────┘        SmartThings 클라우드   LG ThinQ 클라우드   Roborock 클라우드
                                                                 
   [집 안: 선택형 홈 에이전트] ══(집에서 서버로 "나가는" 연결만)══▶ 서버   (LAN 기기: 삼성 TV 로컬 등)
```

핵심 아이디어:
- 앱은 지금처럼 "**기기 목록 / 기능(capability) / 명령**"이라는 **공통 언어**로만 말합니다. 서버도 같은 언어를 씁니다. 그래서 **앱 화면은 그대로**이고 연결 대상만 바뀝니다.
- 서버 안의 기기 제어 코드는 `hub/homehub/adapters/`(SmartThings, Roborock, LG ThinQ, `cloud_base.py`)를 **가져다 씁니다**. 지금은 "토큰을 파일 하나로 저장"하는 구조(`secret_store.py`)라서, 서버용으로는 **"사용자별로 DB에 암호화 저장"** 하는 부분만 새로 만들면 됩니다.

### 2-2. 추천 기술 스택 (단순함 우선)

| 역할 | 추천 | 이유 |
|---|---|---|
| API 서버 | **Python + FastAPI** | 이미 허브가 FastAPI. 어댑터 코드를 그대로 재사용 가능 |
| 데이터베이스 | **PostgreSQL** | 사용자·구독·감사로그 같은 "돈과 관련된 기록"에 안정적 |
| 대기열/속도 제한 | **Redis** (처음엔 생략하고 Postgres만으로 시작해도 됨) | 호출 제한, 백그라운드 작업 |
| 백그라운드 작업 | **arq 또는 Celery** 중 하나 | 상태 확인, 푸시 발송, 토큰 갱신 |
| 배포 | **Docker + 단일 서버(VPS) 또는 관리형 서비스** | 초기엔 서버 1~2대로 충분. 데이터는 한국 리전 권장 |
| 암호 키 관리 | 클라우드 **KMS** (AWS KMS / GCP KMS 등) | 4장 참고 |
| 푸시 | **APNs(iOS) / FCM(Android)** | 표준 |
| 앞단 보호 | Cloudflare 등 CDN/방화벽 | 기본적인 디도스·봇 방어 |
| 관리자 화면 | 처음엔 **SQLAdmin 같은 관리 화면 라이브러리**, 커지면 별도 제작 | 6장 |
| 모니터링 | Sentry(오류) + 기본 서버 지표 | 장애를 빨리 알기 위해 |

일부러 **쿠버네티스·마이크로서비스는 쓰지 않습니다.** 사용자가 수백~수천 명이 될 때까지는 "서버 한 덩어리(모놀리스) + DB 하나"가 가장 싸고 고치기 쉽습니다.

### 2-3. 기기 종류별로 서버에 닿는 길

| 기기 종류 | 서버가 닿는 방법 | 집 안 장치 필요? |
|---|---|---|
| **SmartThings 기기** (삼성 가전/TV 등) | SmartThings 클라우드 공식 API. 사용자가 로그인·승인(OAuth)하면 서버가 토큰 보관 | **불필요** (클라우드만) |
| **LG ThinQ 기기** | LG 클라우드 API | **불필요** |
| **Roborock 로봇청소기** | Roborock 클라우드(계정 토큰) 경유. 지도/청소 명령을 서버가 중계 | 대부분 불필요. 단, 로컬 통신을 쓰려면 홈 에이전트 |
| **집 안 로컬 기기** (삼성 TV 웹소켓 제어, 같은 와이파이의 기기 등) | 클라우드에서는 **집 안으로 못 들어옴** → **홈 에이전트**가 필요 | **필요 (선택형)** |

**홈 에이전트(선택형, 가벼운 프로그램)**:
- 지금의 `hub/`를 **"서버에 나가는 연결만 하는 가벼운 버전"** 으로 줄인 것. 라즈베리파이/NAS/미니PC에서 실행.
- 집 공유기에 **포트를 열지 않습니다.** 에이전트가 서버로 먼저 연결(웹소켓/MQTT)을 걸어 두고, 서버가 그 통로로 명령을 내려보냅니다. (통신사 CGNAT 환경에서도 동작, 보안상 안전. `ROADMAP.md` Phase 4의 "클라우드 릴레이" 방식과 같습니다.)
- 서버는 이 통로를 **사용자별로 분리**(다른 사람의 에이전트에는 절대 명령 불가)해야 합니다.
- **클라우드 기기만 쓰는 사용자는 에이전트 없이도** Pro/Max 기능 대부분을 쓸 수 있게 하는 것이 목표입니다. 에이전트는 "로컬 기기까지 원격 제어하고 싶은 분"을 위한 선택지입니다.

### 2-4. 푸시 알림 (예: 세탁 완료)

1. 서버 작업자가 사용자의 기기 상태를 **주기적으로 확인**(폴링)하거나, 클라우드가 지원하면 **이벤트/웹훅**을 받음. (SmartThings/ThinQ의 이벤트 방식 지원 범위는 개발 시작 전에 확인 필요. 처음엔 폴링으로 시작.)
2. "세탁 중 → 완료"처럼 **상태가 바뀐 순간**을 감지.
3. 사용자의 폰 등록값(푸시 토큰)으로 **APNs(iOS) / FCM(Android)** 에 발송 요청.
4. 앱이 알림을 표시. 알림에는 개인정보(기기 이름 등)를 최소한만 담습니다.

폴링은 클라우드 호출량(=SmartThings 요금/제한에 영향)을 늘리므로 1-2절의 "확인 주기"로 통제합니다.

### 2-5. 앱 쪽 변경(참고)

- 앱의 백엔드 인터페이스에 `PremiumBackend`를 추가: 로그인 → 서버 주소로 기기 목록/명령 호출.
- 앱은 **서버가 응답하지 않으면 자동으로 무료(직접 연결) 모드로 동작**할 수 있게 둡니다. (서버 장애 = 앱 전체 마비가 되지 않도록.)

## 3. 로그인/계정(인증)

### 3-1. 지원할 로그인 방식

| 방식 | 비고 |
|---|---|
| 이메일 + 비밀번호 | 기본. 비밀번호는 **argon2id** 등 표준 방식으로 해시 저장(원문 저장 절대 금지) |
| Google 로그인 | 표준 OIDC |
| Facebook 로그인 | 표준 OAuth. (Facebook은 이메일을 안 주는 경우가 있어 처리 필요) |
| **Sign in with Apple** | 아래 참고 |

**Apple 규칙 (2026-09-29 확인)**: 앱스토어 심사 지침 4.8은 Google/Facebook 같은 **소셜 로그인을 넣으면, 동등한 "개인정보 보호형 로그인"도 함께 제공**하라고 합니다. 예전에는 "Sign in with Apple을 반드시 넣어라"였지만 2024년 1월에 "같은 조건(이름·이메일만 수집, 이메일 숨김 가능, 광고용 추적 안 함)을 만족하는 다른 로그인도 가능"으로 완화되었습니다. 그러나 **실무적으로는 Sign in with Apple을 넣는 것이 가장 안전**(심사 거절 위험 최소)하므로 이 문서에서는 넣는 것으로 정합니다.
- 참고: 앱이 계정 만들기를 지원하면 **앱 안에서 계정 삭제**가 가능해야 함(지침 5.1.1(v)). Sign in with Apple로 만든 계정은 삭제 시 Apple의 토큰 폐기(revoke) 호출도 필요. Google Play도 앱 내 삭제 경로 + 웹 삭제 안내를 요구합니다.

### 3-2. 토큰(JWT) 방식

- **액세스 토큰**: 수명 짧음(예: 15분). 서버 요청 때마다 첨부.
- **리프레시 토큰**: 수명 길음(예: 30~60일). **한 번 쓰면 새것으로 교체(회전)** 하고, 이미 쓴 토큰이 다시 오면 **탈취로 간주해 그 로그인 세션 전체를 폐기**.
- 리프레시 토큰은 DB에 **해시로만** 저장. 폰에는 OS 보안 저장소(iOS Keychain / Android Keystore)에 보관.
- 기기별 로그인 목록을 두고, 사용자가 "다른 기기에서 로그아웃"을 할 수 있게 함.

### 3-3. 이메일 인증 · 비밀번호 재설정

- 가입 시 **이메일 인증 링크**(유효 시간 짧게, 1회용). 미인증 계정은 유료 기능 구매 불가.
- 비밀번호 재설정: 1회용·짧은 유효 링크. 재설정하면 **모든 기존 로그인 세션 폐기**. 계정 존재 여부가 드러나지 않게 "메일을 보냈습니다"로 동일 응답.
- 이메일 발송은 외부 서비스(예: AWS SES 등) 사용. 발신 도메인 SPF/DKIM 설정 필요.
- Apple의 "이메일 숨기기(릴레이 주소)"를 쓰는 사용자도 있으므로 **이메일 주소가 실제 주소가 아닐 수 있음**을 전제로 설계.
- 같은 이메일로 여러 로그인 방식이 만나는 경우(계정 연결) 정책 필요: **이메일이 인증된 경우에만** 자동 연결(남의 계정 가로채기 방지).

### 3-4. 남용 방지 (Rate limiting)

| 대상 | 초안 규칙(가정치) |
|---|---|
| 로그인 시도 | IP당 + 계정당 각각 제한(예: 5회 연속 실패 시 점점 길어지는 대기) |
| 가입 | IP당 시간당 몇 건으로 제한 + 봇 방지(캡차) 검토 |
| 비밀번호 재설정/인증 메일 | 계정당 시간당 3회 |
| 일반 API | 1장 표의 티어별 한도 |
| 결제 검증 | 사용자당 제한 (스토어 API 호출 절약) |

## 4. 보안

### 4-1. 제3자 토큰(SmartThings/ThinQ/Roborock) 암호화 저장

서버에서 가장 위험한 자산은 **사용자의 집 기기를 조종할 수 있는 토큰**입니다. 유출되면 남의 집 가전을 조종할 수 있기 때문입니다.

**봉투 암호화(Envelope Encryption)** — 쉽게 말하면 "열쇠를 넣은 금고를 또 다른 금고에 넣기":
1. 토큰마다(또는 사용자마다) **데이터 키(DEK)** 를 만들어 토큰을 암호화(AES-256-GCM 등).
2. 그 데이터 키를 다시 **클라우드 KMS의 마스터 키(KEK)** 로 암호화해서 DB에 함께 저장.
3. 마스터 키는 **KMS 밖으로 절대 나오지 않고**, 서버는 복호화가 필요할 때만 KMS에 "이 키 풀어줘"라고 요청.
4. 결과: **DB만 유출돼도** 토큰을 읽을 수 없음. KMS 호출 기록이 남으므로 이상 접근 추적 가능. 마스터 키는 정기적으로 교체(로테이션) 가능.

### 4-2. 그 밖의 원칙

- **최소 권한**: 서버 프로세스·DB 계정·관리자 각각 필요한 권한만. 예) 결제 검증 코드는 기기 토큰을 읽을 수 없게 분리. 관리자 화면에서도 **토큰 원문은 볼 수 없음**(연결 상태만 표시).
- **요청 범위 최소화**: SmartThings 등 OAuth 승인 시 **필요한 권한(scope)만** 요청. 예) 알림만 쓰는 Pro 사용자에게 "제어" 권한을 요구하지 않는 것도 검토.
- **감사 로그(Audit log)**: 로그인, 비밀번호 변경, 토큰 연결/해제, 구독 변경, 관리자 조회·변경, 환불을 **누가·언제·무엇을** 기록. 수정·삭제 불가 방식(추가만 가능)으로 저장, 일정 기간 보관.
- **비밀값(secrets) 관리**: API 키·DB 비밀번호·Apple/Google 결제 키·JWT 서명 키를 **코드/저장소(git)에 넣지 않음**. 클라우드의 시크릿 관리 서비스 또는 환경 변수로 주입. 서명 키는 주기적으로 교체하고 키 식별자(kid)로 구버전 허용 기간을 둠. 이 저장소의 `hub/data/`가 커밋 금지인 것과 같은 원칙입니다.
- **전송/저장 보안**: 전 구간 HTTPS(TLS), DB 디스크 암호화, 백업도 암호화, 백업 복구 훈련.
- **로그에 민감정보 금지**: 토큰·비밀번호·영수증 원문을 로그에 남기지 않음.
- **의존 라이브러리 점검**: 취약점 자동 점검(Dependabot 등).
- **테넌트 분리**: 모든 DB 조회에 "이 사용자 것만"이라는 조건을 강제(코드 규칙 + 테스트).
- **사고 대응 계획**: 유출 의심 시 절차(토큰 일괄 폐기, 사용자 통지, 신고) 문서화.

### 4-3. 개인정보 (한국 개인정보 보호법, PIPA) 메모

> ⚠️ 법률 자문이 아닙니다. 사업자 등록 시점 전에 **전문가(변호사/개인정보 컨설턴트) 검토**를 권장합니다. 아래는 개발 시 고려할 체크리스트입니다.

- **수집 최소화**: 이메일, (소셜 로그인 식별자), 기기 목록/상태, 결제 상태 정도. 이름·전화번호·위치 등은 필요 없으면 받지 않음.
- **동의와 고지**: 개인정보 처리방침 공개, 가입 시 필수/선택 동의 분리(마케팅 수신은 별도 선택).
- **국외 이전**: 서버를 해외 클라우드에 두거나, 푸시(APNs/FCM)·이메일·오류 수집(Sentry) 등 해외 서비스에 데이터가 넘어가면 **처리방침에 국외 이전 사실을 공개**해야 할 수 있음. 가능하면 **서버·DB는 국내(서울) 리전**.
- **유출 통지**: 2026년 개정 법 시행(2026-09 시행으로 검색됨 — **원문 확인 필요**)으로, 유출 사실(가능성 포함)을 알게 되면 **72시간 이내 통지** 의무가 강화된 것으로 보임. → 4-2의 사고 대응 계획에 이 시간 기준을 반영.
- **개인정보 보호책임자 지정**과 연락처 공개.
- **보관 기간과 파기**: 목적 달성 시 지체 없이 파기. 단, 전자상거래법상 **결제·계약 기록은 일정 기간(예: 5년) 보관 의무**가 있어 "삭제 vs 보관" 구분표가 필요(정확한 기간은 확인 필요).
- **위탁/제3자 제공 고지**: 결제 대행사, 이메일 발송사, 클라우드 사업자 등 **처리 위탁 업체 목록**을 처리방침에 명시.
- **미성년자**: 만 14세 미만 가입 제한(또는 법정대리인 동의) 정책 필요.

### 4-4. 계정 삭제

- **앱 안에서** "계정 삭제" 버튼 제공(Apple 5.1.1(v), Google Play 정책 모두 요구) + 웹에서도 삭제 요청 가능한 주소 제공(Google Play).
- 삭제 시 처리 순서: (1) 진행 중인 구독 안내(스토어 구독은 **스토어에서 해지해야 요금이 멈춤**을 명확히 안내) → (2) SmartThings/ThinQ/Roborock **토큰 폐기(가능하면 각 사에 revoke 호출) 및 삭제** → (3) 푸시 토큰·기기·기록 삭제 → (4) 법적 보관 의무 있는 결제 기록은 **개인 식별을 최소화해 분리 보관** → (5) Sign in with Apple 사용자는 Apple 토큰 revoke → (6) 감사 로그에는 "삭제 수행" 기록 남김.
- 실수 방지용 **유예 기간(예: 7~14일)** 을 둘지 결정 필요 (열린 질문).
- 백업에 남은 데이터는 백업 만료 주기에 따라 자연 삭제됨을 처리방침에 설명.

## 5. 사용자 토큰 관리 (SmartThings / ThinQ / Roborock 연결)

### 5-1. 연결 방법

| 서비스 | 연결 방식 | 참고 |
|---|---|---|
| **SmartThings** | **OAuth**: 앱이 SmartThings 로그인 화면을 열고 사용자가 "허용" → 서버가 승인 코드를 받아 토큰으로 교환 | 액세스 토큰 수명 약 **24시간**, 리프레시 토큰 약 **30일**(SmartThings 개발자 문서). 갱신 때마다 새 리프레시 토큰을 받으므로 **서버가 항상 최신 것으로 교체 저장**해야 함. 개인용 임시 토큰(PAT)은 24시간짜리라 상용에 부적합 |
| **LG ThinQ** | 사용자 계정 승인 방식(개발 시 공식 절차·상업 이용 조건 **확인 필요**) | 현재 허브의 `lg_thinq.py` 방식과 서버 방식이 다를 수 있음 |
| **Roborock** | 현재 코드는 사용자 계정으로 클라우드 로그인(인증 코드) 후 토큰 확보 | **비공식**. 아래 5-4 참고 |

연결 흐름(공통):
1. 앱에서 "SmartThings 연결" → 2. 공급사 로그인/동의 화면 → 3. 서버가 토큰 수령 → 4. **봉투 암호화 후 저장(4-1)** → 5. 기기 목록 동기화 → 6. 앱에 "연결됨" 표시.
- 사용자 비밀번호는 **절대 서버가 받지 않는 방식(OAuth)** 을 우선합니다. Roborock처럼 계정 입력이 불가피한 경우 **비밀번호는 저장하지 않고 토큰만** 저장하며, 그 사실을 화면에서 안내.

### 5-2. 해제(Revoke)

- 앱/웹의 "연결 관리"에서 항목별 **[연결 해제]**: 서버가 (1) 공급사에 토큰 폐기 요청(가능한 경우) (2) 내 DB에서 삭제 (3) 관련 알림/자동화 중지 (4) 감사 로그 기록.
- 사용자가 SmartThings 쪽에서 직접 권한을 취소한 경우, 서버가 갱신 실패로 알아채고 "다시 연결이 필요해요" 푸시를 보내고 상태를 **"재연결 필요"** 로 표시.
- 구독 만료 시: 데이터는 유예 기간 후 삭제하거나, 토큰 갱신만 중지하고 보관하는 정책을 정해야 함 (열린 질문).

### 5-3. 갱신(Rotation)

- **자동 갱신(Pro 이상의 핵심 가치)**: 서버가 만료 전(예: 남은 시간 25% 시점)에 미리 갱신. 갱신 실패 시 재시도 → 그래도 실패하면 사용자에게 재연결 안내.
- **동시성 주의**: 리프레시 토큰은 한 번 쓰면 바뀌므로, 두 작업이 동시에 갱신하면 하나가 실패해 연결이 끊길 수 있음 → **사용자별 갱신 잠금** 필요.
- **우리 서비스의 마스터 키 교체**(KMS 키 로테이션)는 사용자 토큰을 다시 암호화하는 작업으로 정기 수행.
- **Free(서버 없음)** 의 경우 토큰은 **폰에만** 저장되고, 30일 이상 앱을 안 열면 연결이 끊길 수 있음 → 이것이 Pro 전환의 자연스러운 이유가 됨.

### 5-4. 공식/비공식 리스크 (중요)

- 프로젝트 문서(`ROADMAP.md`의 Legal 항)에 이미 적힌 대로 Roborock(miIO 등)은 **비공식**입니다. 개인 사용은 괜찮아도 **유료 서비스로 제공하면 약관 위반/차단 위험**이 있습니다. → Max의 "Roborock 서버 경유" 기능은 **Roborock 공식 파트너 API 가능 여부 확인 후** 출시하거나, 확인 전까지는 "베타/실험 기능"으로 표시.
- SmartThings: 위 0장 대로 2026-10부터 API 유료화 예정. **개인용 $4.99/월 플랜은 '비상업 개인 개발자' 대상**이므로, 우리처럼 **여러 사용자를 대신해 호출하는 서비스는 상업용 요금제/파트너 계약 대상일 가능성이 큽니다.** 그 요금은 1장의 가격표(특히 Pro 1,000원)를 근본적으로 흔들 수 있어 **출시 전 최우선 확인 사항**입니다. (참고: 공식 블로그 2026-06-23 공지. 사용자가 자기 SmartThings 계정으로 앱을 통해 쓰는 경우와 우리 서버가 대행하는 경우의 과금 주체가 어떻게 나뉘는지 SmartThings 측에 문의 필요.)

## 7. 결제

### 7-1. 반드시 알아야 할 사실 (2026-09-29 웹 확인)

**Apple (iOS 앱)**
- 앱 안에서 파는 **디지털 구독은 원칙적으로 Apple 인앱결제(IAP)** 를 써야 합니다. (예외적으로 허용되는 지역 규정이 있으나 한국은 아래.)
- 수수료: 표준은 **30%**, 구독 **가입 1년 후부터 15%**. **App Store Small Business Program**(연 수익 100만 달러 미만, **신청해야 적용**)에 가입하면 **처음부터 15%**. 한국 스토어에서도 동일하게 15% 적용 가능(가입 승인 후 적용 시점은 약간 지연).
- 한국은 전기통신사업법 개정으로 **제3자 결제 허용**: 별도 자격(StoreKit External Purchase Entitlement) 신청, **한국 스토어 전용 별도 앱 빌드**가 필요하고 같은 앱에서 Apple IAP와 병행 불가, 수수료 **26%** (Apple 페이지 기준) 및 월별 보고. → 1,000원 요금제에는 **오히려 불리하거나 비슷**하고 운영 부담만 커서 **비추천**.
- 서버 검증: Apple **App Store Server API** + **App Store Server Notifications V2**(서명된 JWS 알림) 사용. Apple이 제공하는 **App Store Server Library(Python 등)** 로 서명 검증.

**Google Play (Android 앱)**
- 디지털 구독은 **Google Play 결제** 사용이 원칙(한국은 사용자 선택 결제 허용 제도 있음).
- 수수료: 한국은 **2026-12-31까지 자동 갱신 구독 15%**. **2026-12-31부터** 새 구조로 바뀌어 **서비스 수수료 10% + Google Play 결제 사용 시 결제 수수료 5% = 약 15%**(대체 결제 사용 시 5% 면제)로 발표됨. (Google Play Console 도움말/공식 블로그 기준. 세부는 재확인 필요.)
- 서버 검증: **Google Play Developer API**(구독 상태 조회) + **Real-time Developer Notifications(Cloud Pub/Sub)** 수신.

**웹 결제(선택, 앱 밖에서 결제)**
- Toss Payments(국내 카드/간편결제 정기결제) 또는 Stripe(해외 카드).
- **주의점**
  - 앱 안에서 웹 결제로 **유도하는 버튼/링크**는 스토어 정책 제한이 있음. 한국·미국·EU 등 지역별 규칙이 계속 바뀌므로 **출시 시점에 재확인**하고, 처음엔 "앱 안에서 웹 결제 안내 금지"로 안전하게 시작하는 것을 권장.
  - 웹으로 결제한 사용자는 스토어의 환불/구독관리 기능을 못 쓰므로 **직접 환불·청약철회·영수증·현금영수증/세금계산서·부가세 처리**를 해야 함.
  - 통신판매업 신고, 사업자등록, 전자상거래법 준수(청약철회, 고지 의무) 필요.
  - PG(결제대행) 수수료는 계약 조건에 따라 다름(대략 몇 % 수준이라고만 이해하고 **계약 전 견적 필요**).
- 장점: 수수료가 스토어보다 낮을 수 있음. 단점: 앱 심사 리스크, 운영 부담, 사용자 결제 이탈.

### 7-2. 서버 쪽 결제 처리 흐름 (스토어 결제)

1. 사용자가 앱에서 구독 구매 → 스토어가 결제 처리.
2. 앱이 서버에 "구매 정보(거래 ID/토큰)" 전달.
3. 서버가 **스토어 서버에 직접 확인**(Apple Server API / Google Developer API). **앱이 보내준 값을 그대로 믿지 않음.**
4. 확인되면 사용자 티어와 만료일을 DB에 기록.
5. 이후 갱신·해지·환불·결제 실패(유예 기간)는 **스토어 알림(웹훅)** 으로 받아 자동 반영: Apple `DID_RENEW`, `EXPIRED`, `REFUND`, `DID_FAIL_TO_RENEW` 등 / Google RTDN.
6. 알림이 누락되어도 대비해 **정기적으로 상태 재조회(대사, reconcile)**.
- **멱등성**: 같은 알림이 두 번 와도 결과가 같도록(알림 ID 저장).
- **구독 ↔ 계정 연결**: 구매 시 앱이 우리 계정 ID를 스토어 거래에 붙여(Apple `appAccountToken`, Google `obfuscatedAccountId`) 누구의 구독인지 확실히 연결.
- **계정 복원**: 새 폰에서 "구매 복원" 지원.
- Apple 샌드박스/테스트 환경과 실제 환경을 분리하여 검증.

### 7-3. 1,000원 요금제는 남는 게 거의 없다 (개산, **추정치**)

한국 스토어 표시가격에는 부가세(VAT 10%)가 포함됩니다. 아래는 이해를 돕기 위한 **대략적 산수**이며 실제 정산액은 스토어 정산 보고서로 확인해야 합니다.

| 단계 | Pro 1,000원 기준 (추정) |
|---|---|
| 표시가격 | 1,000원 |
| 부가세 제외 | 약 909원 |
| 스토어 수수료 15% 차감 | 약 770원 안팎 |
| 종합소득세/법인세, 결제 오류·환불 등 | 추가로 감소 |
| 서버·푸시·이메일·KMS·모니터링·SmartThings API 비용 등 | 사용자 1인당 얼마가 들지에 따라 **적자 가능** |

- 30% 수수료(소규모 사업자 프로그램 미가입 시)라면 약 640원 안팎.
- 또한 **스토어에서 1,000원이 실제 선택 가능한 가격 단계인지 확인 필요**(스토어는 정해진 가격 단계 중에서 선택). 최종 가격은 통화·세금 규칙에 맞춰 재조정될 수 있음.
- 결론: Pro는 **"돈 버는 상품"이라기보다 "무료 사용자를 유료 습관으로 끌어오는 입문 상품"** 으로 보고, 원가(특히 폴링과 SmartThings API 비용)를 **매우 낮게** 유지해야 함. 연간 결제(할인) 상품이나 가격 상향도 검토.
- **가장 큰 미지수는 SmartThings API 비용(5-4)**: 사용자 1인당 API 비용이 수백 원만 되어도 Pro는 적자입니다.
